# الإضافة الجماعية للدعوات (Invitation Bulk Add)

> RC1 Fix Pack 3A — "Invitation Bulk Add Migration"، مُحدَّث بـ **Blocker
> Fix — Phone-Only Compatibility**. آخر تحديث: 2026-08-01.
> النطاق: نقل قدرة "الإضافة الجماعية" من اللوحة القديمة (Legacy Guest Panel)
> إلى صفحة "إدارة الدعوات" المعتمَدة (Phase 9) — **حصراً**. لا تعديل على
> الحذف الفعلي (Hard Delete)، ولا على أي منطق مُجمَّد آخر (راجع "قيود
> الالتزام" في نهاية هذا الملف).
>
> **Blocker Fix (هذا التحديث):** صفوف "هاتف فقط" كانت تُرفَض في النسخة
> الأولى من هذا الفيكس باك بسبب اشتراط الاسم (راجع §5 أدناه للتفاصيل
> الكاملة). صار الآن **مقبولة بالكامل** عبر اسم عرض مُولَّد حتمياً — **حصراً
> داخل `PGE_Invitation_Bulk_Add_Service`**، بلا أي تغيير على
> `PGE_Invitation_Service::create()`، `PGE_Invitation_Repository::create()`،
> أو نموذج "إضافة دعوة" المفردة (لا يزال يشترط الاسم كما هو).

---

## 1. لماذا؟

قبل هذا الفيكس باك، كانت "الإضافة الجماعية" (لصق عدة أرقام دفعة واحدة)
متاحة فقط في لوحة "إدارة المدعوين" القديمة (`page-event-manage.php` /
`event-guests.php`) — وهي أحد سببَين وحيدَين (مع الحذف الفعلي) أبقيا اللوحة
القديمة "مساراً نشطاً" وفق قرار [RC1-AUDIT.md §14.1](./RC1-AUDIT.md) (A4).
هذا الفيكس باك يبني نسخة إنتاجية جديدة من الإضافة الجماعية داخل معمارية
"Host Invitation Management" المعتمَدة، بحيث يبقى **الحذف الفعلي وحده** هو
سبب بقاء اللوحة القديمة.

## 2. المعمارية

```
Host Invitation Management UI (templates/event-invitations.php)
    ↓ AJAX (pge_invitation_mgmt_bulk_preview / pge_invitation_mgmt_bulk_confirm)
Authorized Invitation AJAX Controller (includes/invitation-management-ajax.php)
    ↓ يُفوِّض التحليل/التحقّق إلى
PGE_Invitation_Bulk_Add_Service (includes/class-pge-invitation-bulk-add.php)
    ↓ لكل صف صالح — إنشاء عبر الخدمة القائمة نفسها بلا أي تعديل عليها
PGE_Invitation_Service::create()
    ↓
PGE_Invitation_Repository::create()
    ↓
Existing Guest Storage (`_pge_invited_guests` post meta، عبر event-guests.php)
```

`PGE_Invitation_Bulk_Add_Service` **لا تكتب شيئاً بنفسها** — هي طبقة
Parser/Validator خالصة. كل كتابة فعلية تمرّ حصراً عبر
`PGE_Invitation_Service::create()` الحالية، صفاً صفاً، بلا أي نسخة ثانية من
منطق إنشاء الدعوة.

## 3. صيغ الإدخال (Input Formats)

textarea واحد، سطر واحد لكل دعوة، ثلاث صيغ مدعومة فقط:

| الصيغة | مثال |
|--------|------|
| هاتف فقط | `0500000000` |
| اسم + فاصلة + هاتف | `أحمد محمد,0500000000` |
| اسم + تبويب + هاتف | `أحمد محمد␉0500000000` |

- **لا رفع ملفات، لا CSV، لا Excel** في هذه المرحلة (ممنوع صراحة).
- الأسطر الفارغة (أو التي تحتوي مسافات فقط) **تُتجاهَل تماماً** — لا تُحسَب
  صفاً، لا تُنتج خطأً.
- المسافات الزائدة حول القيم (الاسم/الهاتف) تُطبَّع (`trim()`) قبل التحقّق.
- سطر يحتوي **فاصلة وتبويباً معاً**، أو أكثر من فاصلة/تبويب واحد، يُعتبَر
  سطراً غير مفهوم (`malformed_ambiguous_separator` / `unsupported_extra_columns`)
  ولا يُحلَّل كهاتف/اسم — يظهر في المعاينة كصف غير صالح مع سببه.

## 4. التحليل (Parsing) — `PGE_Invitation_Bulk_Add_Service::parse()`

دالة مُخصَّصة واحدة، لا منطق تحليل داخل القالب. تُعيد صفوفاً مُهيكَلة:

```php
[
  'line_number'      => int,     // رقم السطر الفعلي في النص الأصلي (قبل تجاهل الفارغة)
  'guest_name'       => string,
  'phone'            => string,  // كما أُدخِل (مُطبَّع مسافياً فقط)
  'normalized_phone' => string,  // عبر pge_norm_phone() الحالية — بلا نسخة ثانية
  'status'           => 'valid' | 'invalid' | 'duplicate_in_batch' | 'duplicate_in_event',
  'error'            => string|null, // رمز عمل مستقر، أو null إذا صالح
]
```

تطبيع الهاتف يُعاد استخدامه حرفياً من `pge_norm_phone()` (`helpers.php`) —
لا دالة تطبيع ثانية.

## 5. التحقّق (Validation)

كل صف يُتحقَّق منه **مستقلاً** — فشل صف واحد لا يُسقِط الدفعة كاملة.

| الفحص | رمز الخطأ عند الفشل |
|-------|----------------------|
| الهاتف موجود بعد التطبيع | `phone_missing` |
| الهاتف لا يتجاوز 20 رقماً بعد التطبيع | `phone_too_long` |
| الاسم (المُقدَّم أو **المُولَّد تلقائياً** — راجع أدناه) لا يتجاوز 190 حرفاً | `name_too_long` |
| لا فاصلة وتبويب معاً في نفس السطر | `malformed_ambiguous_separator` |
| لا أكثر من عمودين (فاصلة أو تبويب) | `unsupported_extra_columns` |
| لا تكرار داخل الدفعة نفسها | `duplicate_in_batch` |
| لا تكرار مع دعوة موجودة فعلاً في نفس المناسبة | `duplicate_in_event` |

> ملاحظة: رمز الخطأ `name_required` **لم يعد موجوداً في الكود إطلاقاً** بعد
> Blocker Fix (راجع القسم التالي) — `parse()` لا يُنتجه بعد الآن تحت أي
> ظرف.

### قرار معماري مُحدَّث (Blocker Fix): اسم عرض مُولَّد حتمياً لصفوف "هاتف فقط"

**القرار الأصلي** (Fix Pack 3A، قبل هذا التحديث) كان رفض صفوف "هاتف فقط"
بسبب اشتراط `PGE_Invitation_Repository::create()` اسماً غير فارغ:

```php
if ($normalized_name === '') {
    return ['result' => 'error', 'reason' => 'invalid_name'];
}
```

هذا القيد **لا يزال قائماً بلا أي تغيير** — راجع §"لا تغيير في العقد العام"
أدناه. الفرق أن `PGE_Invitation_Bulk_Add_Service` أصبح الآن **يُولِّد اسم
عرض تلقائياً** لصفوف "هاتف فقط" **قبل** استدعاء `create()`، بدل رفضها.

**القاعدة التجارية الصريحة (RFC لاحق، عكَس القرار الأصلي):** *"Phone-only
rows MUST be accepted in Bulk Add. Do NOT relax the name requirement for
normal single-invitation creation. The exception applies ONLY inside
`PGE_Invitation_Bulk_Add_Service`."*

#### صيغة الاسم المُولَّد

```
"ضيف — {آخر 4 أرقام من الهاتف المُطبَّع}"
```

مثال: الهاتف `0501234567` → الاسم `"ضيف — 4567"`.

المُنفِّذ الفعلي — `PGE_Invitation_Bulk_Add_Service::generate_display_name()`:

```php
public static function generate_display_name(string $normalized_phone): string
{
    $last_digits = substr($normalized_phone, -4);
    return 'ضيف — ' . $last_digits;
}
```

**حتمية كاملة (Deterministic)، بلا أي عشوائية أو طابع زمني** — نفس رقم
الهاتف يُنتج نفس الاسم دائماً، في كل استدعاء لـ`parse()`، سواء في المعاينة
أو في التأكيد.

**Fallback للأرقام الأقصر من 4:** `substr($s, -4)` في PHP تُعيد **كامل**
السلسلة تلقائياً إذا كان طولها أقل من 4 أحرف — يُحقِّق قاعدة *"if fewer
than 4 digits, use all available digits"* بلا أي فرع شرطي إضافي. مثال:
الهاتف `123` (بعد التطبيع) → الاسم `"ضيف — 123"`.

**لا هاتف قابل للاستخدام إطلاقاً (بعد التطبيع = سلسلة فارغة):** الصف يبقى
`invalid` بسبب `phone_missing` — **قبل** أي محاولة توليد اسم. توليد الاسم
لا يتجاوز التحقّق من الهاتف إطلاقاً (راجع ترتيب الفروع في `parse()` أدناه).

**لا اسم افتراضي ثابت مكرَّر** مثل `"ضيف بدون اسم"` — كل رقم يُنتج اسماً
مختلفاً (آخر 4 أرقامه هو)، مما يمنع تصادم الأسماء بين ضيوف مختلفين داخل
نفس المناسبة.

#### الخصوصية: لماذا آخر 4 أرقام فقط؟

الاسم المُولَّد **لا يكشف الهاتف الكامل** — لا في المعاينة، ولا في التخزين،
ولا في أي مكان يُعرَض فيه اسم الضيف (مثلاً لضيوف آخرين قد يرون قائمة
الحضور). آخر 4 أرقام كافية لتمييز الضيف عن غيره داخل نفس الدفعة/المناسبة
دون كشف الرقم بالكامل — نفس مبدأ إخفاء جزئي شائع (مثل عرض "•••• 4567" لبطاقة
دفع). **مُتحقَّق منه تنفيذياً** في الاختبارات (BF6، BF6ب): لا الرقم الكامل
ولا حتى البادئة السابقة لآخر 4 أرقام تظهر داخل الاسم المخزَّن.

#### حتمية المعاينة↔التأكيد (Preview/Confirmation Determinism)

المعاينة (`preview()`) والتأكيد (`confirm()`) يستدعيان **نفس دالة `parse()`
على نفس النص الملصوق الخام** — التأكيد **لا يقبل ولا يثق بأي اسم مُولَّد
يُرسِله المتصفح**؛ فقط `raw_text` الخام. بما أن التوليد حتمي بالكامل (لا
عشوائية)، فإن الاسم الذي يُعرَض في المعاينة **يطابق تماماً** الاسم الذي
يُخزَّن فعلياً عند التأكيد — بلا أي كود إضافي مطلوب لضمان هذا التطابق (نفس
نمط "لا ثقة بنتيجة المعاينة من العميل" المطبَّق أصلاً على باقي حقول الصف —
راجع §7). **مُتحقَّق منه تنفيذياً** في الاختبار BF4.

#### لا تغيير في العقد العام (No Global Contract Change)

- `PGE_Invitation_Service::create()` — **لم يُلمَس إطلاقاً**، ولا يستدعي
  `generate_display_name()` بأي شكل.
- `PGE_Invitation_Repository::create()` — **لم يُلمَس إطلاقاً**، لا يزال
  يرفض الاسم الفارغ برمز `invalid_name` دون أي استثناء.
- نموذج "إضافة دعوة" المفردة (`pge_invitation_mgmt_create_handler` +
  `templates/event-invitations.php`) — **لا يزال يشترط الاسم كما هو
  بالضبط**؛ إنشاء دعوة مفردة بهاتف بلا اسم لا يزال يُرفَض بـ`invalid_name`.
  **مُتحقَّق منه تنفيذياً** في الاختبار BF17.
- التوليد التلقائي **حصري بالكامل** داخل `PGE_Invitation_Bulk_Add_Service`
  — لا يُستدعى من أي ملف آخر في المشروع. **مُتحقَّق منه تنفيذياً** في
  الاختبار BF18 (فحص بنيوي: `class-pge-invitation-service.php` و
  `class-pge-invitation-repository.php` لا يحتويان على السلسلة
  `generate_display_name` إطلاقاً).

**هذا يُزيل الفرق السلوكي السابق عن اللوحة القديمة** (`event-guests.php`
bulk_add، التي كانت تسمح بأسماء فارغة صراحة `'name' => ''`) — الإضافة
الجماعية الجديدة أصبحت الآن **تُغطي فعلياً** كل ما كانت تدعمه اللوحة
القديمة، بما في ذلك صفوف "هاتف فقط"، دون الحاجة لتعديل عقد الإنشاء العام
أو اختراع مسار إنشاء ثانٍ.

## 6. المعاينة (Preview)

خطوتان إلزاميتان: **Parse & Preview** ثم **Confirm Creation**. المعاينة
(`pge_invitation_mgmt_bulk_preview`) **قراءة فقط بالكامل** — لا إنشاء دعوة
واحدة، مهما كانت نتيجة التحقّق.

تعرض لكل صف: رقم السطر، الاسم (**بما فيه الاسم المُولَّد تلقائياً لصفوف
"هاتف فقط"، مثل `"ضيف — 4567"`، قبل أي تأكيد** — راجع §5)، الهاتف، الحالة،
سبب الخطأ إن وُجد. وملخصاً: `{total, valid, invalid, duplicate}`.

## 7. التأكيد (Confirm) — بلا أي ثقة بنتيجة المعاينة من المتصفح

`pge_invitation_mgmt_bulk_confirm` **لا يقبل مصفوفة صفوف جاهزة من العميل
إطلاقاً** — فقط النص الملصوق الخام (`raw_text`) نفسه. الخادم يُعيد
`parse()` + `check_duplicates()` من الصفر، بالضبط كأول مرة، قبل أي معالجة.
أي صف "يبدو صالحاً" في حمولة الطلب بلا أن يكون كذلك فعلياً بعد إعادة الحساب
الخادمي **لا يُنشأ إطلاقاً** — بنيوياً مستحيل تجاوز هذا من طرف العميل.

هذا ينطبق أيضاً على **الاسم المُولَّد** لصفوف "هاتف فقط" (Blocker Fix):
الخادم **لا يقبل ولا يثق بأي اسم مُولَّد يُرسِله المتصفح** — `parse()` تُعيد
توليده من الصفر عبر `generate_display_name()` من رقم الهاتف الموجود داخل
`raw_text` نفسه. بما أن التوليد حتمي بالكامل، يتطابق الاسم المُخزَّن فعلياً
مع الاسم الذي ظهر في المعاينة تماماً (راجع §5).

خطوات Confirm:
1. إعادة التحقّق من التفويض (`pge_mgmt_validate_request()` المشتركة — A9).
2. إعادة تحليل وتحقّق كل صف من الصفر.
3. إعادة فحص التكرار (مقابل الحالة الحالية للمناسبة).
4. لكل صف "صالح" فقط: إنشاء فعلي عبر `PGE_Invitation_Service::create()`.

## 8. سياسة المعالجة الأفضل-جهد (Best-Effort / Atomicity Policy)

**لا معاملة ذرية على مستوى الدفعة بأكملها.** كل صف صالح يُعالَج بشكل مستقل.
فشل صف واحد (تحقّق أو إنشاء) **لا يُراجع أو يُلغي** الدعوات التي أُنشئت
بنجاح سابقاً في نفس الدفعة. نتيجة لكل صف:

| النتيجة | المعنى |
|---------|--------|
| `created` | أُنشئت الدعوة فعلياً. |
| `duplicate` | تكرار (داخل الدفعة، مع المناسبة، أو حالة سباق حقيقية أعادها `create()` نفسها). |
| `invalid` | فشل تحقّق (تنسيق/اسم مفقود/هاتف غير صالح إلخ) — لم تُحاوَل الإنشاء إطلاقاً. |
| `failed` | استثناء غير متوقَّع أثناء الإنشاء (نادر، دفاعي) — يُسجَّل تشخيصياً (بلا اسم/هاتف) عبر `error_log()` بنفس اصطلاح A21، ولا يُوقف بقية الدفعة. |

## 9. التزامن (Concurrency) — فجوة موجودة مسبقاً، لم تُخترَع هنا ولم تُحَل

`PGE_Invitation_Repository::create()` يقرأ `pge_event_guests_get_map()`
(post meta)، يتحقّق من التكرار في الذاكرة، ثم يكتب
`pge_event_guests_save_map()` — **بلا أي قفل (`GET_LOCK`/transient)
إطلاقاً**. هذا يعني أن طلبين متزامنين (سواء عبر "إضافة دعوة" المفردة أو عبر
الإضافة الجماعية، أو كلاهما معاً) يمكن نظرياً أن يتسبَّبا بـ"تحديث مفقود"
(Lost Update).

**هذه فجوة قائمة أصلاً في مسار الإنشاء الحالي بالكامل — لم تُنشَأ هنا.**
تبعاً لتعليمات RFC الصريحة ("report the gap before changing unrelated
architecture. Do not invent a second duplicate rule")، **لم يُضَف أي قفل
جديد** خاص بالإضافة الجماعية — كان سيُنشئ قاعدة حماية ثانية مختلفة عن
القاعدة الحالية غير الآمنة للتزامن أصلاً في المسار المفرد. `confirm()`
تُعيد استخدام `PGE_Invitation_Service::create()` حرفياً صفاً صفاً — نفس
مستوى الأمان (أو انعدامه) الموجود مسبقاً بالضبط.

**الأثر العملي:** لصق نفس الرقم في طلبين متزامنين منفصلين (نافذتَي متصفح،
أو دفعة جماعية + إضافة مفردة في اللحظة نفسها) قد يؤدي نادراً لتكرار غير
مُكتشَف. هذا خطر موجود مسبقاً في الإنتاج، موثَّق هنا كمخاطرة صريحة، لا
كعيب جديد.

## 10. التدقيق (Audit)

- كل دعوة تُنشأ بنجاح ضمن الدفعة تُسجِّل حدث **`created`** الفردي الحالي
  بنفسه، عبر `PGE_Invitation_Service::create()` **بلا أي تعديل عليه**.
- بعد انتهاء المعالجة (بغضّ النظر عن العدد): حدث تدقيق واحد إضافي على
  مستوى المناسبة **`bulk_create_completed`**، يحمل حصراً:
  `{actor_user_id, event_id, total, created, duplicate, invalid, failed, timestamp}`
  (الأربعة الأخيرة مُرمَّزة JSON داخل عمود `reason` النصي الموجود أصلاً —
  نفس نمط `export_completed`، بلا تعديل على بنية الجدول).
- **لا يُخزَّن النص الملصوق الخام، ولا اسم مدعو (سواء مُقدَّم يدوياً أو
  مُولَّد تلقائياً)، ولا رقم جوال فردي** في سطر `bulk_create_completed` —
  مُتحقَّق منه تنفيذياً في الاختبارات (21، 21ب، 21ج، BF16، BF16ب). الاسم
  المُولَّد (Blocker Fix) قد يظهر فقط ضمن حدث `created` الفردي الحالي إن
  كان هذا المسار يُخزِّن الاسم أصلاً — **تحقَّق فعلياً أنه لا يُخزِّنه**
  (`PGE_Invitation_Management_Audit::record()` لحدث `created` لا يمرِّر
  الاسم إطلاقاً، فقط `event_id`/`guest_phone`/`actor_user_id`/`action`).
- `guest_phone` لسطر `bulk_create_completed` = سنتينل ثابت جديد
  `PGE_Invitation_Management_Audit::EVENT_LEVEL_BULK_ADD_SENTINEL`
  (`__event_bulk_add__`) — مستقل عن سنتينل التصدير `__event_export__`.

## 11. الحدود التشغيلية (Limits)

| الحد | القيمة | الثابت |
|------|--------|--------|
| أقصى عدد أسطر فعلية لكل دفعة | 500 | `PGE_Invitation_Bulk_Add_Service::MAX_LINES` |
| أقصى حجم للنص الملصوق بالكامل | 100,000 بايت (~100KB) | `MAX_PAYLOAD_BYTES` |
| أقصى طول اسم | 190 حرفاً | `MAX_NAME_LENGTH` |
| أقصى عدد أرقام للهاتف بعد التطبيع | 20 رقماً | `MAX_PHONE_DIGITS` |

**لا اقتطاع صامت.** تجاوز حد الحجم أو عدد الأسطر يرفض **الطلب بأكمله**
برسالة واضحة (`payload_too_large` / `too_many_lines`) — لا معالجة جزئية
لأول 500 سطر. حدود الاسم/الهاتف تُطبَّق على مستوى الصف الواحد فقط (لا
تُسقِط الدفعة).

## 12. الأمان

- كل مخرَجات المعاينة/النتيجة تمرّ عبر `escapeHtml()` الحالية في القالب
  قبل إدراجها في DOM — **لا `innerHTML` خام لأي حقل من النص الملصوق**
  (مُتحقَّق منه بنيوياً في الاختبارات، البند 18).
- رسائل الخطأ رموز عمل مستقرة ونصوص عربية ثابتة — **لا كشف لأي تفاصيل
  تنفيذ داخلية**.
- التفويض: نفس `pge_mgmt_validate_request()` المشتركة (تسجيل الدخول +
  nonce + ملكية المناسبة) — لا فحص تفويض ثانٍ منفصل.
- الحدود المذكورة أعلاه تحمي من حمولات ضخمة/عدد أسطر غير معقول.

## 13. الانتقال من اللوحة القديمة (Legacy Transition)

> **تحديث بعد RC1 Fix Pack 3B ("Legacy Guest Panel Retirement — Hard Delete
> Migration"):** القسم أدناه يوثِّق حرفياً حالة اللوحة القديمة كما كانت
> **في نهاية Fix Pack 3A/Blocker Fix فقط** (مرحلة انتقالية سابقة) — أُبقي
> بلا تعديل كسجلّ تاريخي. الحذف الفعلي (فردياً وجماعياً)، وهو "السبب
> الوحيد المتبقّي" المذكور أدناه، **نُقل هو الآخر بالكامل** لصفحة إدارة
> الدعوات في Fix Pack 3B — واجهة CRUD كاملة (إضافة/تعديل/حذف) استُبدلت
> بإشعار انتقالي وحيد، وبطاقة واتساب وحدها بقيت بلا تغيير. A4 الآن **مُغلَقة
> بالكامل (Fully Resolved)** — راجع [`RC1-AUDIT.md` §16](./RC1-AUDIT.md)
> للتفاصيل الكاملة.

شريط التوجيه أعلى لوحة "إدارة المدعوين" القديمة (`page-event-manage.php`)
كان يقول (Fix Pack 3A): *"الإضافة الجماعية متوفّرة الآن في صفحة إدارة
الدعوات ... اللوحة أدناه باقية مؤقتاً فقط من أجل الحذف الفعلي."*

في تلك المرحلة، **لم يكن قد حُذف أو عُطِّل أي عنصر من اللوحة القديمة نفسها**
— نموذج الإضافة الجماعية القديم (`bulkGuestForm`)، الإضافة الفردية،
التعديل، الحذف الفردي/الجماعي كانت كلها لا تزال موجودة وقابلة للتنفيذ
فعلياً. **الحذف الفعلي فقط** كان ما تبقّى كسبب نشاط اللوحة القديمة حينها.

## 14. ما لم يُلمَس (Scope Guard)

لا رفع ملفات، لا استيراد CSV/Excel، لا أي تغيير على الحذف الفعلي (سلوكاً
أو إزالة)، لا إشعارات (واتساب/SMS/بريد)، لا تغيير على معمارية QR، الحضور،
الإحصاء، أو التصدير. لم يبدأ Fix Pack 3B.

**Blocker Fix (هذا التحديث) — نطاق إضافي لم يُلمَس:** لا تعديل على
`PGE_Invitation_Repository::create()` قواعد التحقّق العامة، لا تعديل على
نموذج "إضافة دعوة" المفردة، لا تعديل على نموذج التدقيق (لا يزال
`bulk_create_completed` يخزِّن عدادات فقط)، لا إعادة تصميم للتزامن (نفس
الفجوة الموثَّقة في §9 قائمة كما هي)، لا بدء لـFix Pack 3B.
