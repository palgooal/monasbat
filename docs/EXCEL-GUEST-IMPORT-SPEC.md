## 1. المكان الصحيح لدمج الميزة

الميزة **لا** تحتاج أي طبقة جديدة. البنية الحالية جاهزة تماماً لاستيعابها كامتداد أفقي لما هو موجود، بنفس نمط "الإضافة الجماعية" (Bulk Add):

| الطبقة | الملف | الدور بالنسبة للاستيراد |
|---|---|---|
| **UI / Modal** | `templates/event-invitations.php` | زر جديد `📥 استيراد من Excel` بجانب زر `openBulkAddBtn`، ونافذة Modal جديدة بنفس نمط `bulkAddModal` (state machine: رفع → تحقق → معاينة → تنفيذ → نتيجة) |
| **AJAX Controller** | `includes/invitation-management-ajax.php` | 3 إجراءات جديدة فقط: `pge_invitation_mgmt_excel_template` (تنزيل النموذج)، `pge_invitation_mgmt_excel_preview` (تحقق + معاينة)، `pge_invitation_mgmt_excel_confirm` (تنفيذ الاستيراد) — كل واحد يستخدم `pge_mgmt_validate_request()` كما تفعل بقية الإجراءات تماماً |
| **Service جديد (تنسيقي فقط)** | ملف جديد `class-pge-invitation-excel-import.php` بنفس مكانة `class-pge-invitation-bulk-add.php` | **لا يضيف مدعوين بنفسه**. مسؤوليته فقط: قراءة الملف → تحويله لصفوف نصية (name, phone, note) → تمرير هذه الصفوف لنفس منطق `PGE_Invitation_Bulk_Add_Service` (تحقق التكرار، الملخص، والتنفيذ عبر `PGE_Invitation_Service::create()`) |
| **Guest Creation Service (بلا تغيير)** | `class-pge-invitation-service.php` → `PGE_Invitation_Service::create()` | **نفس نقطة الإدخال الوحيدة** التي يمر منها أي مدعو، يدوياً كان أو من الإضافة الجماعية أو من Excel |
| **Repository (بلا تغيير)** | `class-pge-invitation-repository.php` | لا لمس إطلاقاً |
| **Audit (بلا تغيير في الآلية)** | `class-pge-invitation-management-audit.php` | إعادة استخدام السجل الموجود، انظر القسم 2 |

**الخلاصة**: "استيراد Excel" ليس ميزة جديدة معمارياً — هو **مصدر بيانات بديل (Alternate Input Adapter)** يغذّي نفس خط أنابيب `PGE_Invitation_Bulk_Add_Service` الموجود فعلاً. الفرق الوحيد بينه وبين اللصق النصي الحالي هو مصدر السطور: بدل `raw_text` من `<textarea>`، تكون السطور مستخرجة من ملف Excel.

## 2. كيف ستستفيد من النظام الحالي (إعادة الاستخدام بالتفصيل)

| الحاجة | الحل الموجود المُعاد استخدامه | بدون أي تعديل عليه |
|---|---|---|
| إضافة مدعو واحد فعلياً | `PGE_Invitation_Service::create($event_id, $phone, $name, $note, $actor_user_id)` | ✅ يُستدعى كما هو، سطراً سطراً |
| تطبيع الجوال | `pge_norm_phone()` (helpers.php) | ✅ نفس الدالة الوحيدة في المشروع |
| فحص التكرار داخل نفس المناسبة | `pge_event_guests_get_map($event_id)` + منطق `check_duplicates()` في `PGE_Invitation_Bulk_Add_Service` | ✅ يُعاد استخدامه كما هو لإنتاج حالة "موجود مسبقاً" |
| السماح بنفس الرقم في مناسبة أخرى | سلوك ضمني — الفحص مرتبط بـ `$event_id` فقط، فلا حاجة لأي كود إضافي | ✅ يعمل تلقائياً لأن الفحص أصلاً scoped بالمناسبة |
| توليد Invitation Code | داخل `pge_event_guests_save_map()` تلقائياً عند غياب الكود | ✅ لا استدعاء يدوي مطلوب من مسار الاستيراد |
| توليد QR | Lazy، عبر `qr_version` في `_pge_invitation_status`، منفصل تماماً عن الإنشاء | ✅ لا كود QR في مسار الاستيراد إطلاقاً |
| Audit | `PGE_Invitation_Management_Audit::record()` | ✅ انظر التوصية أدناه |
| Quota | **لا يوجد أي إنفاذ Quota عند إنشاء مدعو في كل الكودبيس الحالي** — `guest_limit` يُفحص فقط لاحقاً عند الرد بـ RSVP في `rsvp-handler.php` | ✅ الاستيراد يرث نفس السلوك الحالي تلقائياً بدون أي كود جديد (ليس تجاوزاً — هذا هو سلوك النظام القائم فعلياً لكل مسارات الإضافة) |
| توليد اسم افتراضي عند غياب الاسم | **غير مطبَّق هنا** — الاسم إجباري بنص المستخدم صراحة، بخلاف Bulk Add القديم الذي يسمح بجوال فقط | ⚠️ فرق متعمد عن Bulk Add — الاسم عمود إجباري في نموذج Excel |

**قرار Audit نهائي (محسوم)**: إعادة استخدام نفس Action الموجود `bulk_create_completed` (بدل إنشاء Action جديد)، مع payload محدود صراحة لحقلين فقط:
```json
{"source": "excel", "count": 142}
```
**لا يُخزَّن `filename` ولا أي بيانات وصفية أخرى عن الملف داخل سجل الـ Audit** — الـ Audit يوثّق فعل "استيراد جماعي" وعدده فقط، وليس مصدر الملف أو اسمه، تقليلاً لأي بيانات غير ضرورية داخل سجل دائم. هذا يبقي `ACTIVE_ACTIONS_PHASE_9C` بلا تعديل، ولا يضيف قيمة جديدة لقائمة `ACTIONS` الثابتة — أقل تدخل ممكن في طبقة الـ Audit المُحكمة.

## 3. هل توجد مكتبة Excel حالياً؟

**لا.** تم التحقق من هذا بثلاث طرق مستقلة:
1. لا يوجد `composer.json` في المشروع بالكامل (Glob فارغ).
2. لا يوجد مجلد `vendor/` أو أي إشارة لـ `PhpSpreadsheet` في أي مكان.
3. الملف الوحيد الذي يتعامل مع صيغة XLSX حالياً هو `class-pge-xlsx-writer.php`، وتعليقه العلوي يوثّق صراحة أن اختيار الفريق السابق كان **بناء Writer يدوي بدون أي مكتبة خارجية** (بدون حتى `ext-zip`/`ext-zlib`) — وهذا يؤكد أن نمط المشروع المتبع هو الاعتماد الصفري على مكتبات خارجية، وليس فقط غياب مؤقت لمكتبة.

هذا الملف **Writer فقط** (يبني xlsx) ولا يوفر أي قدرة على **القراءة/التحليل (Parsing)** — لا يمكن الاستفادة منه لقراءة ملف مرفوع من المستخدم.

تم البحث والتحقق من بيانات المكتبة مباشرة من المصدر الرسمي (GitHub) بتاريخ إعداد هذه الوثيقة:

|---|---|---|

| **المصدر الرسمي** | https://github.com/shuchkin/simplexlsx | 1.8k Stars، 489 Fork، 214 Commit — مؤشر صيانة صحي |
| **الإصدار المستقر الحالي** | `1.1.16` (آخر تاغ منشور) | نشط الصيانة، آخر تحديث حديث |
| **الرخصة** | MIT | متوافقة تماماً مع الاستخدام في مشروع تجاري بلا قيود |

| **التعامل مع Empty Cells** | تُرجَع كعناصر فارغة ضمن مصفوفة الصف (سلوك قياسي متوقع) | يُتحقَّق منه في اختبارات Phase 2 |
| **Date Cells التي قد تظهر بالخطأ** | المكتبة تُطبّق تحويلاً تلقائياً للخلايا ذات تنسيق تاريخ رقمي عبر `rows()` (باستخدام `setDateTimeFormat()`, افتراضياً صيغة ISO) | **مخاطرة محتملة إن طبّق Excel تنسيق تاريخ تلقائياً على خلية جوال بالخطأ** — لذلك سياسة القراءة (القسم 4.1) تعتمد على `rowsEx()` حصراً لعمود الجوال، وليس على القيمة الجاهزة من `rows()`، لتفادي أي تحويل تلقائي قبل أن نطبّق سياستنا الخاصة |
| **حماية/حدود التعامل مع ZIP/XML كبير الحجم** | غير موثَّقة كحدود مدمجة في المكتبة نفسها | **الحماية تقع على مستوى المشروع لا المكتبة** — عبر حد أقصى لحجم الملف وعدد الصفوف يُنفَّذ في Phase 7 (Hardening)، بصرف النظر عن أي قارئ يُستخدم |
| **حالة الصيانة الحالية** | نشطة (تاغ حديث، تفاعل مستمر على GitHub) | معيار مطمئن لاعتمادها في ميزة إنتاجية طويلة الأمد |

**لماذا لم تُقترَح `PhpSpreadsheet`؟** لأنها تتطلب Composer إلزامياً + امتدادات إضافية (`ext-zip`, `ext-xml`, `ext-gd` في بعض المسارات) + حجم أكبر بكثير — تخالف صراحة نمط "الاعتماد الصفري على مكتبات خارجية" الذي يتبعه المشروع في `class-pge-xlsx-writer.php`. **لا يوجد سبب حالي لاستخدامها**، وتبقى فقط كخيار طوارئ مستقبلي مذكور نظرياً في حال ثبت لاحقاً (بعد Phase 2 الاختباري) أن `SimpleXLSX` غير كافية أمنياً أو صيانياً — وهو غير متوقَّع بناءً على الفحص أعلاه.

**بند تحفّظ صريح**: لم تُضَف أي مكتبة فعلياً في هذه المهمة — هذا القسم توثيق واختيار فقط، بانتظار الموافقة قبل تنزيل/تضمين أي ملف في المشروع.

### الصيغ المدعومة (نهائي)

| الصيغة | القرار |
|---|---|
| `.xlsx` | ✅ مدعومة — عبر `shuchkin/simplexlsx` (ملف مفرد بلا Composer) |
| `.csv` | ✅ مدعومة — عبر `fgetcsv()` / `str_getcsv()` من PHP الأساسي مباشرة، بلا أي مكتبة |
| `.xls` (الصيغة الثنائية القديمة) | ❌ **غير مدعومة في الإصدار الأول — قرار نطاق صريح**. لا يوجد قارئ خفيف موثوق بلا مكتبات ضخمة لهذه الصيغة (PhpSpreadsheet هي الحل الوحيد الموثوق لـ `.xls` وتتطلب Composer). النموذج الرسمي الذي يُصدِّره النظام نفسه (القسم 5) سيكون `.xlsx` فقط، وواجهة الرفع تعرض رسالة خطأ عربية واضحة إن رفع المستخدم ملف `.xls` |

## 5. المخطط المعماري الكامل للميزة

```
┌─────────────────────────────────────────────────────────────────────┐
│  UI — event-invitations.php                                         │
│  زر "📥 استيراد من Excel"  →  excelImportModal (نمط bulkAddModal)   │
│  الحالات: Upload → Validating → Preview → Importing → Result        │
└───────────────┬─────────────────────────────────────────────────────┘
                │ 1) تنزيل نموذج
                ▼
     GET/AJAX  pge_invitation_mgmt_excel_template
     → يبني xlsx بثلاثة أعمدة "الاسم | رقم الجوال | ملاحظة" عبر PGE_Xlsx_Writer::build() (موجود)
       + عمود "رقم الجوال" مُنسَّق كـ Text Cell صراحة (انظر 5.1)
                │
                │ 2) المستخدم يرفع ملف xlsx/csv
                ▼
     POST  pge_invitation_mgmt_excel_preview   (multipart/form-data + nonce + event_id)
     → pge_mgmt_validate_request()  [نفس الحارس الحالي: login + nonce + ownership]
     → Validate file (امتداد + MIME حقيقي + حجم أقصى) قبل أي تخزين
     → Store temporary raw file على القرص في مجلد معزول مخصص (انظر 5.3)
     → Create transient مربوط بـ user_id + event_id يشير لمسار الملف (انظر 5.2)
       ويُعاد upload_token فقط للمتصفح (وليس file_path ولا أي بيانات صفوف كمصدر ثقة لاحق)
     → Parse: PGE_Invitation_Excel_Import_Service::parse_file($path)
         → يحوّل كل صف إلى نفس شكل سطر Bulk Add: [name, phone, note]
         → يطبّق Phone Column Contract أثناء التحويل (انظر 5.1)
     → إعادة استخدام PGE_Invitation_Bulk_Add_Service::check_duplicates() + summarize()
         (بعد تمرير الصفوف الممثّلة، لا نص خام — يحتاج تعديل بسيط بالتوقيع
          ليقبل array بدل raw_text، بلا تغيير أي منطق داخلي)
     → Preview: استجابة بتقرير الأعداد + جدول Preview (اسم/جوال/ملاحظة/حالة ✅/⚠)
                │
                │ 3) المستخدم يضغط "استيراد N مدعو"
                ▼
     POST  pge_invitation_mgmt_excel_confirm   (nonce + event_id + upload_token فقط — لا شيء غير ذلك)
     → Revalidate authorization: pge_mgmt_validate_request() [نفس الحارس، بلا استثناء]
     → Reload transient بمفتاح upload_token
         → تحقق: transient موجود؟ user_id مطابق للمستخدم الحالي؟ event_id مطابق لباراميتر الطلب؟
         → أي فشل بأي شرط → رفض فوري بدون قراءة أي ملف
     → استخدام file_path المخزَّن داخل الـ transient حصراً (لا file_path من المتصفح إطلاقاً)
     → Reparse: PGE_Invitation_Excel_Import_Service::parse_file() من نفس الملف الخام من جديد
         (لا ثقة بأي بيانات من الـ Preview السابق — نفس مبدأ Bulk Add confirm())
     → حلقة: لكل صف صالح  →  PGE_Invitation_Bulk_Add_Service → PGE_Invitation_Service::create(...)
         (بلا أي INSERT مباشر، بلا Repository جديد)
     → Existing Repository / Invitation Lifecycle (بلا تغيير)
     → PGE_Invitation_Management_Audit::record($event_id, EVENT_LEVEL_BULK_ADD_SENTINEL,
           $actor_user_id, 'bulk_create_completed', json_encode(['source'=>'excel','count'=>$n]))
     → Delete (بعد النجاح أو الفشل النهائي، دائماً): الملف المؤقت من القرص + الـ transient نفسه
     → استجابة: نتيجة نهائية (نجح/فشل لكل صف) → UI Refresh لجدول المدعوين
```

**نقطة تصميم حرجة**: بخلاف Bulk Add (حيث raw_text يُعاد إرساله كاملاً مع كل طلب من المتصفح)، ملف Excel لا يُعاد رفعه مع كل طلب. الحل: تخزين الملف مؤقتاً على السيرفر عند خطوة Preview، والإشارة إليه بـ `upload_token` معتم (GUID عشوائي، غير قابل للتخمين)، مربوط بـ `event_id` + `user_id` عبر WordPress Transient (تفاصيل 5.2). خطوة `confirm` **تعيد التحليل من الملف نفسه على القرص**، ولا تثق مطلقاً بأي مصفوفة صفوف أو مسار ملف قادم من المتصفح — هذا يحافظ حرفياً على نفس مبدأ الثقة الصفرية بالعميل الموجود في `PGE_Invitation_Bulk_Add_Service::confirm()` الحالي.

## 5.1 Phone Column Contract (عقد عمود رقم الجوال)

### مشكلة Excel المعروفة
برنامج Excel يُطبّق تلقائياً تنسيق "General/Number" على أي خلية تحتوي أرقاماً فقط، مما يسبب ثلاث مشاكل صامتة عند الحفظ: حذف الصفر الأول (`0599...` ← `599...`)، تحويل الرقم لصيغة علمية (`9.66599E+11`) للأرقام الطويلة، أو فقدان الشكل الأصلي (فواصل، أقواس) الذي كتبه المستخدم.

### الحل عند مصدر النموذج (Template)
عمود **"رقم الجوال"** في ملف `.xlsx` الرسمي الذي يُنتجه `pge_invitation_mgmt_excel_template` **يجب أن يكون منسّقاً كـ Text Cell** (تنسيق الخلية `@`) وليس `General`/`Number`. هذا يمنع Excel من تطبيق أي تحويل رقمي على القيم التي يكتبها المستخدم في هذا العمود مستقبلاً — طالما بقي المستخدم داخل نفس العمود المنسَّق ولم يلصق بيانات بتنسيق مختلف فوقه.

> **ملاحظة تقنية غير محسومة بعد (تُحل في Phase 1 التنفيذي)**: لم يتم التأكد من قدرة `PGE_Xlsx_Writer::build()` الحالية على ضبط تنسيق خلية/عمود كـ Text (`numFmt="@"`) — الملف الذي قُرئ من هذا الـ Writer سابقاً يبني محتوى أساسياً بلا تدقيق لقدرات التنسيق المتقدمة. إن لم تدعمها الكتابة الحالية، ستحتاج توسعة صغيرة (لا تزال بلا مكتبة خارجية) عند التنفيذ الفعلي في Phase 1 — هذا **ليس قراراً معمارياً جديداً**، بل تفصيل تنفيذي يُتحقق منه حين يبدأ الكود الفعلي.

### سياسة القراءة (عند التحليل الفعلي للملف المرفوع)
تُستخدَم `rowsEx()` من `SimpleXLSX` حصراً لعمود الجوال (وليس `rows()` المبسّطة)، لأنها تكشف حقل `type` الخام لكل خلية:

| حالة الخلية (بحسب `type` من `rowsEx()`) | القرار |
|---|---|
| `type === 's'` (Shared String — الخلية نصية فعلاً) | ✅ تُمرَّر القيمة كما هي حرفياً إلى `pge_norm_phone()` مباشرة — هذا هو المسار المتوقَّع والسليم عند الالتزام بالنموذج الرسمي |
| القيمة الخام تحتوي حرف `E`/`e` بصيغة علمية (مثل `9.66599E+11`) | ❌ **رفض فوري، بدون أي محاولة استخلاص** — الصف يُصنَّف "رقم غير صالح" في تقرير المعاينة |
| `type` رقمي (فارغ/`n`) لكن بدون صيغة علمية ظاهرة | ❌ **يُصنَّف "رقم غير صالح" أيضاً** — رغم أن القيمة قد تبدو سليمة ظاهرياً، لا توجد طريقة برمجية للتأكد أن Excel لم يحذف صفراً بادئاً بصمت قبل الحفظ. القرار المتعمَّد هنا: **"غير مُثبَت أنه سليم" يُعامَل كـ "غير صالح"**، تطبيقاً حرفياً لتعليمة "لا تخمّن الرقم" — لا نبني أي منطق تخمين لاسترجاع صفر مفقود بناءً على طول الرقم أو نمط كود الدولة |

**لا يُسمح بأي محاولة تخمين أو استرجاع رقم فقد Excel جزءاً من شكله الأصلي.** أي صف يقع في الحالتين المرفوضتين أعلاه يظهر في Preview بحالة "⚠ رقم غير صالح" ويُستبعد تلقائياً من الاستيراد، دون حظر بقية الصفوف الصالحة في نفس الملف.

## 5.2 upload_token Binding (آلية تخزين وربط الرمز المؤقت)

**الآلية: WordPress Transient قياسي، بلا أي جدول أو تخزين جديد.**

```
مفتاح الـ Transient:  pge_excel_import_{token}
محتواه (array مُسلسَل تلقائياً بواسطة set_transient):
{
  "user_id":   <int>,   // معرّف المستخدم الذي رفع الملف
  "event_id":  <int>,   // المناسبة المستهدفة
  "file_path": <string>,// المسار الكامل للملف المؤقت على القرص (انظر 5.3) — لا يُرسَل للمتصفح أبداً
  "file_type": <string>,// "xlsx" أو "csv"
  "created_at":<int>    // timestamp لحظة الرفع
}
TTL: 1 ساعة (HOUR_IN_SECONDS) — عبر set_transient(..., ..., HOUR_IN_SECONDS)
```

`token` نفسه: قيمة عشوائية غير قابلة للتخمين (مثل `wp_generate_password(32, false)` أو `bin2hex(random_bytes(16))`) — هي الجزء الوحيد الذي يراه المتصفح ويُعاد إرساله لاحقاً في `confirm`.

**تسلسل `confirm` الإلزامي (بالترتيب، بلا تجاوز أي خطوة)**:
1. يستقبل الطلب `upload_token` فقط — لا `file_path`، لا صفوف، لا أي بيانات ملف أخرى.
2. `pge_mgmt_validate_request()` — نفس الحارس الحالي (login + nonce + ownership على `event_id` المُرسَل بالطلب) يُنفَّذ أولاً وبلا استثناء.
3. `get_transient('pge_excel_import_' . $token)` — قراءة البيانات المخزَّنة.
4. إن لم يوجد transient (منتهي الصلاحية أو token خاطئ) → رفض فوري برسالة واضحة ("انتهت صلاحية الجلسة، يرجى إعادة الرفع").
5. تحقق `current_user_id === $stored['user_id']` — رفض فوري إن لم يتطابق (لا يجوز لمستخدم آخر تأكيد رفعة لم يقم بها، حتى لو كان مالك مناسبة أخرى).
6. تحقق `$request_event_id === $stored['event_id']` — رفض فوري إن لم يتطابق.
7. استخدام `$stored['file_path']` **حصراً** لإعادة فتح وتحليل الملف الخام من جديد — لا ثقة بأي بيانات أخرى.
8. بعد النجاح أو الفشل النهائي (أياً كانت النتيجة) → **حذف كلٍّ من**: الملف الفعلي من القرص (`unlink`) **و** الـ transient نفسه (`delete_transient`) — تنظيف كامل في كل الأحوال، لا يُترَك أي أثر معلَّق.

**لا يُسمح بتمرير `file_path` من المتصفح تحت أي ظرف** — هذا هو الضمان الجوهري الذي يمنع مستخدماً من الإشارة لملف تعسفي على السيرفر.

## 5.3 Temporary File Storage Strategy (استراتيجية تخزين الملف المؤقت)

### القرار: مجلد مخصص داخل `wp-content/uploads/pge-excel-import/`، وليس `sys_get_temp_dir()`/`wp_tempnam()`

**المقارنة والسبب**:

| الخيار | التقييم |
|---|---|
| **`sys_get_temp_dir()` / `wp_tempnam()`** | ❌ **غير مُوصى به هنا**. المسار الفعلي الذي يُرجعه `wp_tempnam()`/`get_temp_dir()` في ووردبريس **غير مضمون** — يعتمد على أول مسار قابل للكتابة من سلسلة محاولات (`WP_TEMP_DIR` → `sys_get_temp_dir()` → `upload_tmp_dir` من إعدادات PHP → في أسوأ الحالات `wp-content/` نفسه كخيار أخير). على استضافات WordPress المشتركة (وهو نمط الاستضافة الغالب لهذا المشروع)، هذا التذبذب يعني أننا لا نتحكم فعلياً بموقع الملف ولا صلاحيات المجلد ولا نضمن عدم وقوعه ضمن مسار قابل للوصول عبر الويب. كما أن بعض بيئات الاستضافة تُفعِّل `open_basedir` بشكل يمنع الوصول لمسار temp النظام من الأساس |
| **مجلد مخصص `wp-content/uploads/pge-excel-import/`** | ✅ **الخيار المُعتمَد**. مسار متوقَّع ومستقر 100%، داخل حدود تثبيت ووردبريس نفسه (لا مشاكل `open_basedir`)، قابل للكتابة دائماً (لأن `uploads/` أصلاً يجب أن يكون قابلاً للكتابة لعمل ووردبريس بالكامل)، ونتحكم بالكامل في: التسمية (token عشوائي فقط)، الصلاحيات، وملف `.htaccess` حمائي مخصص. يتوافق أيضاً مع نمط المشروع الحالي في التعامل مع ملفات مؤقتة/سجلات (`wp-content/*-webhook.log` مثلاً) — نفس فلسفة "مجلد مخصص تحت تحكمنا" |

**تفاصيل التنفيذ المقرَّرة (توثيق فقط، بلا تنفيذ في هذه المهمة)**:
- المسار: `wp-content/uploads/pge-excel-import/{event_id}/{token}.{xlsx|csv}` — اسم الملف الداخلي = `token` العشوائي نفسه المخزَّن في الـ Transient، **وليس** اسم الملف الأصلي الذي رفعه المستخدم بأي حال (لا يُقرأ ولا يُخزَّن اسم الملف الأصلي إطلاقاً).
- **لا يُستخدَم `wp_handle_upload()` بمساره الافتراضي** (الذي يضع الملف داخل مجلد `uploads/YYYY/MM/` العام القابل للوصول العام) — بل نقل الملف يدوياً (`move_uploaded_file()` بعد تحقق أمان قياسي) إلى المجلد المخصص أعلاه فقط.
- **الملف غير مسجَّل في Media Library إطلاقاً** — لا يُستدعى `wp_insert_attachment()` ولا أي دالة تُنشئ Post من نوع `attachment`. الملف موجود على القرص فقط، بلا أي أثر في قاعدة البيانات غير الـ Transient.
- **لا يُعاد أي Public URL** للملف في أي استجابة AJAX — فقط `upload_token` المعتم.
- **حماية ضد التنفيذ**: ملف `.htaccess` مخصص داخل `pge-excel-import/` يمنع تنفيذ PHP (`php_flag engine off` أو `<FilesMatch>` تمنع أي امتداد قابل للتنفيذ) ويمنع الوصول المباشر لأي ملف داخل المجلد بالكامل (`Deny from all` / `Require all denied`) — بنفس فلسفة `.htaccess` الحالي في جذر المشروع الذي يمنع تنزيل `*.zip|tar|gz|bak|sql|env|log`.
- **الحذف**: فوري بعد `confirm` (نجاحاً أو فشلاً) + Cron احتياطي (Phase 7) يحذف أي ملف أقدم من TTL الـ Transient (ساعة واحدة) في حال لم يُكمل المستخدم دورة الاستيراد إطلاقاً (أغلق المتصفح مثلاً).

## 6. Template Contract (عقد النموذج الرسمي) + رحلة المستخدم خطوة بخطوة

### عقد النموذج (نهائي، محسوم)

النموذج الرسمي **3 أعمدة بالضبط، لا أكثر ولا أقل**:

| # | العمود | الإلزامية | ملاحظة |
|---|---|---|---|
| 1 | الاسم | **Required** | لا يُقبل صف بدون اسم — يُصنَّف "صف غير صالح" |
| 2 | رقم الجوال | **Required** | منسَّق كـ Text Cell إلزامياً في النموذج المُصدَّر (انظر 5.1)، يمر عبر `pge_norm_phone()` بعد تحقق سلامة النوع |
| 3 | ملاحظة | **Optional** | يجوز أن تكون فارغة دون أن يُصنَّف الصف غير صالح |

**ترتيب الأعمدة ثابت في هذا الإصدار الأول** (Column Order = index ثابت: عمود 0 = اسم، عمود 1 = جوال، عمود 2 = ملاحظة) — القراءة تعتمد على ترتيب العمود الفعلي في الملف وليس على مطابقة نص الهيدر، مع تحقق أن الصف الأول فعلاً هيدر متوقَّع كطبقة حماية إضافية (انظر جدول المخاطر، القسم 7).

### رحلة المستخدم خطوة بخطوة

1. المستخدم في صفحة إدارة الدعوات يضغط **📥 استيراد من Excel**.
2. تُفتح Modal تعرض: منطقة رفع ملف + زر **تحميل نموذج Excel**.
3. (اختياري) يضغط تحميل النموذج → يحصل على ملف `.xlsx` بأعمدة `الاسم | رقم الجوال | ملاحظة` (3 أعمدة بالضبط، عمود الجوال منسَّق كنص)، يملؤه في برنامج Excel/Sheets.
4. يعود ويرفع الملف المعبّأ (`.xlsx` أو `.csv`).
5. فور الاختيار، **لا استيراد فوري** — تظهر حالة "جارٍ التحقق..." ويُرسَل الملف لـ `pge_invitation_mgmt_excel_preview`.
6. تظهر شاشة تقرير التحقق:
   - عدد الصفوف: 150
   - صالح: 142 ✅
   - مكرر (داخل نفس المناسبة): 4 ⚠
   - رقم غير صالح: 3 ⚠
   - صف فارغ: 1 ⚠
7. أسفل التقرير: جدول Preview كامل — كل صف مع (الاسم / الجوال / الملاحظة / الحالة).
8. زر أسفل الجدول: **استيراد 142 مدعو** (الرقم = عدد الصفوف الصالحة فقط تلقائياً).
9. عند الضغط: حالة "جارٍ الاستيراد..." → استدعاء `pge_invitation_mgmt_excel_confirm`.
10. شاشة نتيجة نهائية: عدد ناجح / عدد فشل (إن وجد) + رسالة "تم استيراد 142 مدعو بنجاح".
11. الـ Modal تُغلَق تلقائياً أو يدوياً → جدول المدعوين في الصفحة يتحدّث فوراً (نفس آلية UI Refresh المستخدمة بعد Bulk Add الحالي).

## 7. جميع المخاطر المحتملة

| الخطر | الشرح | التخفيف المقترح |
|---|---|---|
| **رفع ملفات ضارة** | مستخدم يرفع ملف مموَّه كـ xlsx (مثلاً PHP بامتداد مزيّف) | التحقق من MIME الحقيقي (`finfo`) + امتداد الملف + حجم أقصى (مثلاً 2MB) + تخزين في مجلد محمي غير قابل للتنفيذ (`.htaccess`، انظر 5.3) + عدم الاعتماد على اسم الملف الأصلي إطلاقاً |
| **Race condition بين Preview وConfirm** | المستخدم يرفع ملفاً، ثم يعدّله ويرفع ملفاً آخر بنفس الجلسة قبل تأكيد الأول | كل `upload_token` فريد لكل رفعة (transient منفصل)، والـ confirm يتطلب token مطابق تماماً + تحقق user_id/event_id — لا احتمال تداخل |
| **ملفات/transients متروكة (Orphaned)** | مستخدم يرفع ولا يكمل (يغلق المتصفح) | TTL ساعة واحدة على الـ Transient نفسه (يختفي تلقائياً) + Cron دوري احتياطي (Phase 7) لحذف أي ملف فعلي أقدم من الساعة في `uploads/pge-excel-import/` حتى لو تأخر تنظيف الملف عن انتهاء الـ Transient |
| **ملفات ضخمة (مئات/آلاف الصفوف)** | قد تستهلك وقت تنفيذ طويل عند `confirm` وتصطدم بـ PHP `max_execution_time` | حد أقصى معقول لعدد الصفوف (مثلاً 500) يُرفَض بوضوح فوق هذا الرقم في مرحلة Preview |
| **تعارض الأعمدة** | مستخدم يعدّل ترتيب الأعمدة أو يضيف أعمدة في ملف Excel يدوياً | القراءة تعتمد على **ترتيب العمود** (index) وليس اسم الهيدر بالضرورة، مع تحقق أن الصف الأول هو فعلاً هيدر متوقَّع، وإلا رسالة خطأ واضحة "صيغة الملف لا تطابق النموذج الرسمي" |
| **تكرار عبر رفعتين متتاليتين لنفس الملف** | مستخدم يستورد نفس الملف مرتين بالخطأ | فحص التكرار الحالي (`check_duplicates` ضد `pge_event_guests_get_map`) يحمي تلقائياً من إعادة إضافة نفس الجوال داخل نفس المناسبة في المرة الثانية — يظهر الكل كـ "موجود مسبقاً" |
| **فشل جزئي أثناء `confirm`** | صف رقم 80 من 142 يفشل لسبب غير متوقع (خطأ DB مؤقت) | نفس سلوك Bulk Add الحالي: Best-effort بدون Rollback، مع تقرير نهائي دقيق لكل صف (ناجح/فاشل) بدل فشل-كل-شيء-أو-لا-شيء |
| **أرقام جوال في خلايا رقمية غير موثوقة (ليست Text)** | مستخدم يخالف تنسيق النموذج (يلصق بيانات فوق العمود فتُفقَد خاصية Text)، فيحتمل فقدان صفر بادئ بصمت | القرار الحاسم في 5.1: **أي خلية جوال ليست `type=s` تُرفَض كـ"رقم غير صالح" دون استثناء**، بلا أي محاولة تخمين أو استرجاع — أكثر تحفظاً من اللازم أحياناً، لكنه يمنع استيراد أرقام مموَّهة/ناقصة بصمت |
| **قدرة `PGE_Xlsx_Writer` الحالية على تنسيق عمود كـ Text** | غير مؤكَّدة بعد — لم تُفحَص هذه القدرة التفصيلية في الكود الحالي (انظر ملاحظة 5.1) | يُتحقَّق منها فعلياً في بداية Phase 1 التنفيذي؛ إن لزم الأمر تُضاف قدرة تنسيق خلية بسيطة (`numFmt="@"`) للـ Writer نفسه، بلا أي مكتبة خارجية وبلا تغيير في باقي سلوكه |
| **صفوف بأرقام دولية مختلطة** | جوال بدون كود دولة، أو بصيغ مختلفة (+966 مقابل 00966 مقابل محلي) | لا حل جديد مطلوب — نفس `pge_norm_phone()` الحالي يُطبَّق كما هو على كل الأنظمة الحالية بلا استثناء لملف Excel |
| **صلاحيات الوصول للملف المؤقت** | تخمين مسار الملف أو الـ token من مستخدم آخر | اسم الملف = token عشوائي غير متوقَّع (32+ خانة) + الـ transient يحمل `user_id`/`event_id` ويُتحقَّق منهما إلزامياً في `confirm`، وليس فقط وجود الملف أو صحة الـ token شكلياً |

**ملاحظة**: مخاطرة "توفر `ZipArchive`/`ext-zip`" المذكورة في مسودة سابقة من هذه الوثيقة **أُزيلت بعد حسم اختيار المكتبة** — `shuchkin/simplexlsx` (القسم 4) لا تعتمد على `ext-zip` إطلاقاً (فك ضغط داخلي مدمج)، فالمخاطرة لم تعد قائمة.

## 8. خطة التنفيذ المرحلية (كل مرحلة قابلة للاختبار المستقل)

**Phase 0 — تضمين مكتبة القراءة (تمهيدي، بلا أي منطق ميزة)**
- تنزيل ملف `SimpleXLSX.php` المفرد من المصدر الرسمي (`shuchkin/simplexlsx`, الإصدار `1.1.16`, رخصة MIT) وتضمينه في `includes/lib/simplexlsx/SimpleXLSX.php`، بلا Composer وبلا `vendor/`.
- إن ثبت أن `PGE_Xlsx_Writer` الحالية لا تدعم تنسيق خلية كـ Text — توسعتها بأقل تعديل ممكن لدعم `numFmt="@"` على عمود واحد فقط.
- اختبار: تضمين الملف والتأكد أن `SimpleXLSX::parse()` يعمل على ملف xlsx تجريبي بسيط، بلا أي ربط بالميزة بعد.

**Phase 1 — نموذج التنزيل فقط**
- إضافة action واحد `pge_invitation_mgmt_excel_template` يستخدم `PGE_Xlsx_Writer::build()` الموجود (بعد توسعته إن لزم) لإنتاج ملف **بثلاثة أعمدة بالضبط**: "الاسم | رقم الجوال | ملاحظة"، مع تنسيق عمود "رقم الجوال" كـ Text Cell إلزامياً.
- زر "تحميل نموذج Excel" في الصفحة (بدون أي Modal استيراد بعد).
- اختبار: تنزيل الملف، فتحه في Excel، التأكد من الأعمدة الثلاثة، التنسيق النصي لعمود الجوال (كتابة `0599...` والتأكد أن الصفر لا يُحذَف بعد الحفظ وإعادة الفتح)، والترميز (UTF-8 عربي سليم).

**Phase 2 — القارئ (Service) بمعزل عن UI/AJAX**
- إنشاء `class-pge-invitation-excel-import.php` بدالة `parse_file($path): array` تُرجع مصفوفة `[name, phone, note]` لكل صف، تدعم `.xlsx` (عبر `SimpleXLSX::parse()` باستخدام `rowsEx()` لعمود الجوال تحديداً) و`.csv` (عبر `fgetcsv`)، وتُطبِّق Phone Column Contract (القسم 5.1) كاملاً أثناء التحويل.
- اختبارات وحدة مستقلة (unit tests بنمط الاختبارات الحالية في `/tests`) بملفات عينة: ملف سليم (جوال كـ Text)، ملف بصفوف فارغة، ملف بأعمدة مقلوبة، ملف بترميز غير UTF-8، ملف بجوال مكتوب كرقم (Scientific Notation)، ملف بجوال مكتوب كرقم صحيح بلا صيغة علمية (يجب أن يُرفَض أيضاً حسب 5.1)، ملف بنص عربي مكرر (Smoke Test لـ sharedStrings).
- **لا AJAX ولا UI بعد** — الخدمة فقط.

**Phase 3 — دمج مع منطق التحقق/التكرار الموجود**
- تعديل بسيط (أو دالة wrapper) في `PGE_Invitation_Bulk_Add_Service` أو استدعاء مباشر لـ `check_duplicates()`/`summarize()` بتمرير الصفوف الناتجة من Phase 2 بدل `raw_text`.
- اختبار: تمرير صفوف Excel المُحلَّلة يدوياً عبر PHP CLI/سكربت اختبار، والتأكد من تطابق تقرير الأعداد (صالح/مكرر/رقم غير صالح/فارغ) مع التوقع.

**Phase 4 — Endpoint المعاينة (Preview) + تخزين الرفع المؤقت**
- `pge_invitation_mgmt_excel_preview`: نقل الملف يدوياً (`move_uploaded_file()`، **وليس** `wp_handle_upload()` بمساره الافتراضي — انظر سبب القرار في 5.3) إلى مجلد `wp-content/uploads/pge-excel-import/{event_id}/` باسم `token` عشوائي، إنشاء transient `pge_excel_import_{token}` (5.2)، إرجاع `upload_token` + تقرير + جدول Preview فقط.
- إنشاء ملف `.htaccess` حمائي داخل `pge-excel-import/` (منع تنفيذ + منع وصول مباشر) ضمن نفس هذه المرحلة.
- اختبار: رفع فعلي عبر Postman/متصفح، التحقق من إنشاء الملف في المسار الصحيح باسم token فقط (لا اسم الملف الأصلي)، التحقق من محتوى الـ transient، والتأكد أن محاولة فتح رابط الملف مباشرة عبر المتصفح تُرفَض (`.htaccess` يعمل)، وأن الاستجابة تطابق شكل استجابة Bulk Add preview الحالي.

**Phase 5 — Endpoint التأكيد (Confirm) + الاستيراد الفعلي**
- `pge_invitation_mgmt_excel_confirm`: تنفيذ تسلسل التحقق الكامل من 5.2 (nonce+login+ownership → transient → user_id/event_id match)، إعادة قراءة الملف من `file_path` المخزَّن داخلياً، حلقة `PGE_Invitation_Service::create()`، تسجيل Audit، حذف الملف المؤقت **و** الـ transient معاً.
- اختبار: تنفيذ استيراد كامل على مناسبة اختبار، التحقق من: عدد السجلات في `wp_pge_event_rsvps`/`_pge_invited_guests`، وجود `invite_code` تلقائياً لكل مدعو، ظهور سجل `bulk_create_completed` بحقل `source: excel, count: N` (بلا filename) في جدول الـ Audit، واختبار سلبي: محاولة `confirm` بـ token ينتمي لمستخدم آخر أو لمناسبة أخرى تُرفَض.

**Phase 6 — واجهة المستخدم الكاملة (Modal)**
- إضافة زر "📥 استيراد من Excel" + Modal بنمط `bulkAddModal` (حالات: رفع → تحقق → معاينة → استيراد → نتيجة) في `event-invitations.php`.
- ربط الأزرار بالـ 3 Endpoints من المراحل السابقة.
- اختبار: رحلة كاملة يدوية من المتصفح تطابق القسم 6 أعلاه، على الأقل مرتين (ملف سليم بالكامل، وملف بأخطاء مختلطة).

**Phase 7 — تنظيف وحالات حدّية (Hardening)**
- Cron لحذف الملفات المؤقتة اليتيمة.
- حد أقصى لحجم/عدد صفوف الملف مع رسائل خطأ واضحة.
- فحص `ZipArchive` عند الإقلاع + رسالة تشخيصية للأدمن إن غاب.
- اختبار: محاولات رفع متعمّدة لملفات كبيرة/تالفة/بامتداد خاطئ، والتأكد من رسائل خطأ عربية واضحة بدل Fatal Error.

**Phase 8 — مراجعة أمنية ونهائية قبل الإنتاج**
- مراجعة صلاحيات `pge_mgmt_validate_request()` على الثلاث Endpoints.
- مراجعة أن لا مسار جديد للـ INSERT المباشر تسلل خلال أي مرحلة سابقة.
- تشغيل نفس نمط الاختبارات الانحدارية الشامل (regression sweep) المستخدم سابقاً في إصلاح `header_img`، للتأكد أن ميزات أخرى (Bulk Add، الإضافة اليدوية، RSVP) لم تتأثر إطلاقاً.

## Final Architecture Check (مراجعة نهائية للتدفق الكامل)

تم التحقق أن التدفق النهائي بعد كل تحديثات هذه المراجعة يطابق تماماً الترتيب التالي، بلا أي خطوة ناقصة أو مُعاد ترتيبها:

```
Upload
  ↓
Validate file (امتداد + MIME + حجم)
  ↓
Store temporary raw file (مجلد pge-excel-import/ مخصص ومحمي — 5.3)
  ↓
Create transient bound to user+event (pge_excel_import_{token} — 5.2)
  ↓
Parse (SimpleXLSX::rowsEx() لعمود الجوال تحديداً + Phone Column Contract — 5.1)
  ↓
Preview (تقرير الأعداد + جدول بحالة كل صف)
  ↓
Confirm receives token only (لا file_path، لا صفوف من المتصفح)
  ↓
Revalidate authorization (pge_mgmt_validate_request())
  ↓
Reload transient (+ تحقق user_id/event_id)
  ↓
Reparse same raw file (من file_path المخزَّن داخلياً فقط)
  ↓
PGE_Invitation_Bulk_Add_Service (check_duplicates/summarize بمدخلات array بدل raw_text)
  ↓
PGE_Invitation_Service::create()
  ↓
Existing Repository / Invitation Lifecycle (بلا تغيير)
  ↓
Audit bulk_create_completed source=excel (payload: source + count فقط)
  ↓
Delete temp file + transient (دائماً، نجاحاً أو فشلاً)
```

هذا التدفق مطابق حرفياً للترتيب المطلوب. لا توجد فجوة معمارية متبقية بين النقاط الخمس المطلوب إغلاقها وبين محتوى الوثيقة الحالي.

## ملخص الالتزام بالقيود المفروضة

- ✅ لا جدول جديد — كل البيانات تُكتب عبر `pge_event_guests_save_map()` الحالية. الـ Transient ليس جدولاً (آلية WordPress قياسية مدمجة في `wp_options`).
